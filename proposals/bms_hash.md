# BMSの識別(ハッシュ化)における提言

## 最初に結論
0. 例示サンプル
   - 文字列は`UTF-8`エンコードされたバイト列として扱う。
   - BMSファイルが`Shift_JIS`エンコードされている場合は読み込みの時点で`UTF-8`に変換する。
   ```
   #TITLE Hoge
   #ARTIST Piyo

   #WAV01 aaa.wav
   #WAV02 bbb.wav

   #00111:01020A0B
   #00211:01020A0B
   ```
1. テキスト全体を改行文字(`\n`や`\r\n`など)でスライスして配列化する。以下は各スライスについての処理。
   1. 前後の空白(`\x20 \t \r \n \v`など)は削除する。
   2. `#`で**始まらない行**は全て無視する(空行やコメント行の排除)。
   3. **`#`以降最初の空白(`\x20`)またはコロン(`:`)が出現するまでの間**にあるアルファベット(`0x41`-`0x5A`)は全て小文字(`0x61`-`0x7A`)に変換する。
   ```
   ["#title Hoge", "#artist Piyo", "#wav01 aaa.wav", "#wav02 bbb.wav",  "#00111:01020A0B", "#00211:01020A0B"]
   ```
2. `#BASE 62`用の特別処理
   - `#base 62`が存在する(62進BMSである)場合、なにもしない。
   - `#base 62`が存在しない(通常の36進BMSである)場合、`#`の後に数字(`\x30-\x39`)が続く全ての要素について、大文字を小文字に変換する。
   ```
   ["#title Hoge", "#artist Piyo", "#wav01 aaa.wav", "#wav02 bbb.wav",  "#00111:01020a0b", "#00211:01020a0b"]
   ```
3. 配列をバイトごとの辞書順で昇順に並び替える。
   ```
   ["#00111:01020a0b", "#00211:01020a0b", "#artist Piyo", "#title Hoge", "#wav01 aaa.wav", "#wav02 bbb.wav"]
   ```
4. 改行文字`\n`で連結する(※ハッシュ関数に複数の文字列を渡せない場合)。
   ```
   "#00111:01020a0b\n#00211:01020a0b\n#artist Piyo\n#title Hoge\n#wav01 aaa.wav\n#wav02 bbb.wav"
   ```
5. 完成した文字列に対してハッシュ関数を適用する。
   ```
   6e23291c59a95196bca318413abb0f66
   ```
   (一例)
- これはBMSファイル内での「意味の変わらない表記の違い」を全て吸収する。
- ただし`#WAV`定義などにおけるファイル名の大文字/小文字は、この過程では変更されない。
  - ファイルシステムによってはファイル名のcaseは区別されうるためである。
  - この差異も吸収する場合は「ファイル名が記述されている場合は全て小文字にする」などの対応が必要になるが、手順2.に比べて更にコストがかかる。

## なぜこの手順が必要なのか
BMSを遊ぶことができるプログラム(以下「BMSプレイヤー」)において、そのスコアを保存する際には、BMSのファイルパスではなくBMSファイルの内容そのものから生成したハッシュ値をキーとしたデータベースの利用が一般的である。特に事実上の標準となっていた`LR2IR`においては`MD5`ハッシュ値がその識別に使われていた。

`MD5`は暗号学的ハッシュ関数であり、ファイルの内容が1文字でも変わると全く異なる値になる。スコア保存用のキーとして使う場合にもこの性質は好ましいが、一つだけ大きな問題がある。

### 実質に影響しない変更でも「IRが割れる」
例えば以下のような2つのBMS:
```
#TITLE Hoge
#ARTIST Piyo
```
と
```
#ARTIST Piyo
#TITLE Hoge
```
は、意味論的には**完全に同一**にも関わらず、そのバイト列が異なる(記述順が異なる)ために**全く異なる`MD5`値**になる。極端な話、**BMSをエディタで開いてそのまま保存する**だけでもハッシュ値は変わる可能性がある。ハッシュ値が変われば異なる譜面とみなされるため、古いスコアが保存されない。この制約は実用上、大きな障害となりうる。

### 解決策
この問題は、理論的には非常に単純な方法で完全に解決できる。すなわち:
 - 全ての空行とコメント行を**無視**
 - 大文字小文字のような表記揺れが許される場合は**いずれかに統一**
 - 全てのコマンド行を**一貫した順序で並び替え**
 - そうして加工され「厳密化」されたデータに対してハッシュ関数を適用する

これにより例えば「`#TITLE`と`#ARTIST`の位置を交換した」程度の変更はハッシュ値に影響しなくなる。

これまでこのような処理を行うBMSプレイヤーが無かった(あっても主流ではなかった)のは、ひとえに「文字列の編集」が**極めて高負荷な処理**であるためだ。しかし現代の標準的なPCの性能であれば、このくらいの処理はそれほど難しくもないだろう。
